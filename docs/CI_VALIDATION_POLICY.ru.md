# Проверки по риску, без повторных полных прогонов

Этот документ фиксирует решение по замечанию владельца о расходе времени.
Он не отключает существующие CI-проверки: изменение workflows — отдельная
задача после текущей публикации. Успешный тест повторяется при изменении
проверяемого поведения, обнаруженной ошибке или новом существенном риске.

## Локальная работа

| Изменение | Достаточный первый прогон | Когда расширять |
| --- | --- | --- |
| Подпись, высота, отступ, локальный UI-контрол | Затронутый сценарий Chromium и просмотр изменённого состояния | Общий компонент; clipping, focus, touch или различия движков |
| RU/EN и Excel | Чтение/запись, сохранность прежних строк, отображение изменённого термина | Изменение формата импорта/экспорта или общего механизма локализации |
| Данные и расчёты | Табличные проверки модели, затем настоящий расчёт затронутых записей | Общая формула, каталог, условия изучения, снятие бонусов или смена расы/класса |
| Билды, pins, сравнение, PWA | Сохранение/восстановление, старый билд, отдельный получатель, офлайн при изменении кэша | Общий сериализатор, storage, revision или обновление Service Worker |
| Авторизация и серверная запись | Серверные проверки прав/валидации/сессий плюс затронутый UI-путь | Изменение auth, миграций, секретов или схемы хранения |
| Только документация | Ссылки, смысл и формат затронутого документа | Документ содержит исполняемый deployment/config-фрагмент |

Не переносить все числовые сценарии в Firefox/WebKit. Их основной смысл —
проверять поведение браузера: popover/dialog, select, фокус, touch, Esc,
прокрутку, сетевые/offline особенности. Одинаковое вычисление и одинаковую
валидацию данных в первую очередь проверяем в одном движке и чистых тестах.
Настоящая production-проверка остаётся отдельной: локально нельзя доказать,
что Worker и GitHub Pages получили согласованные версии.

## Подтверждённый дубль CI

Сейчас `playwright.config.mjs` запускает основной набор только в Chromium;
отдельный `cross-browser-smoke.spec.mjs` — в трёх движках. Это не три полных
прогона. Но `feature-ci.yml` и `pages.yml` повторяют большие одинаковые группы.

Для PR41 успешный Feature CI `37198517572` занял около 16 минут; из них основной
Chromium-контракт — 298 с, аудит каталога — 197 с, версии/офлайн — 105 с,
69 smoke-проверок — 159 с. Деревья проверенного head
`d3a988f3b7bd4eb6b4c2cad547718d945dfbe8fa` и squash
`a5d2cc6910359288c92a6b1d19c9175e9bbebc4a` идентичны:
`196d549fe69d2b2ea6060cb312e34e586a8d4599`. При этом Pages `37199641421`
по нынешнему workflow всё равно повторяет набор. Это измерение конкретного
запуска, не обещание экономии токенов или weekly usage.

## Безопасный вариант сокращения публикации

Перед изменением Pages нужен проверяемый контракт повторного использования
результата CI. Одного зелёного PR, похожего SHA или имени ветки недостаточно.

- Найти успешный завершённый запуск ожидаемого workflow в этом репозитории
  для проверенного коммита данного PR; не принимать чужой fork или произвольный
  артефакт за свидетельство.
- Сопоставить точное дерево исходников, lockfile, команды и определение проверок,
  фактические версии Node/Python/Playwright и необходимые входы сборки.
- При изменении workflow проверки отдельно подтвердить сам механизм доверия;
  нельзя позволять изменённому коду просто написать себе «проверено».
- При отсутствии/ошибке/несовпадении свидетельства выполнять нынешний полный
  прогон. Прямой push и ручной dispatch не должны случайно обходить защиту.
- Даже при совпадении собрать выпускаемый артефакт, проверить сохранность Legacy,
  версии и обязательные статические контракты; после публикации проверить реальные
  файлы, Worker и один затронутый пользовательский путь.
- Сначала протестировать оба пути: повторное использование и полный fallback;
  отдельно проверить неверное дерево, незавершённый/упавший CI, смену runtime,
  отсутствующий артефакт и изменение workflow. Не ослаблять assertions.

Проверки документации и независимых веток затем можно ограничить path filters
с учётом зависимостей. Общие `js/`, `modern/catalog.js`, сериализация, `package*`,
генераторы, сохранённые данные и workflows нельзя трактовать как локальные правки
одного экрана. Текущий релиз ради этой оптимизации не отменяется.
