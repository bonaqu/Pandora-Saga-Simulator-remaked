# Как проект проверяет изменения

Этот документ объясняет публичную политику качества **Pandora Saga Simulator Remaked**. Цель проверок — развивать Modern-интерфейс и данные, не ломая сохранённый расчётный движок Legacy 2.00, старые билды и основные пользовательские сценарии.

## Проверки зависят от риска изменения

| Что меняется | Основные проверки | Когда нужны дополнительные браузеры / сценарии |
| --- | --- | --- |
| Текст, отступ, локальный UI-контрол | затронутый Chromium-сценарий и проверка состояния | общий компонент, focus, touch, clipping или browser-specific поведение |
| RU/EN и таблица переводов | структура таблицы, сохранность строк, генерация локализации и отображение изменённого текста | меняется формат импорта/экспорта или общий механизм локализации |
| Игровые данные и расчёты | проверки данных и настоящий расчёт затронутых записей | общая формула, каталог, условия изучения, смена класса/расы или снятие бонусов |
| Билды, каталог, PWA/offline | сохранение/восстановление, совместимость старых билдов, версия каталога и кэш | меняется сериализация, storage, Service Worker или сетевое поведение |
| Доступность и браузерный UI | клавиатура, dialog/popover, focus, Esc, scroll/touch | Firefox/WebKit нужны там, где поведение действительно зависит от движка |
| Документация | ссылки, структура и корректность описания | документ участвует в сборке или содержит исполняемую конфигурацию |

Одинаковые числовые формулы не прогоняются без причины во всех браузерах: Chromium несёт основной регрессионный контракт, а Firefox/WebKit в первую очередь проверяют различия браузерного поведения.

## Feature CI

Для pull request проверки разделены на независимые задачи и выполняются параллельно. В них входят:

- Python/Node проверки данных и статических контрактов;
- основной Chromium-контракт, разбитый на shards;
- отдельные проверки каталогов и public projections;
- focused browser smoke для Chromium, Firefox и WebKit;
- PWA/offline и визуально-чувствительные пользовательские сценарии.

Итоговый aggregate-job считается успешным только после всех обязательных частей.

## Публикация GitHub Pages

Обычный merge может использовать уже полученный результат Feature CI, но только если система доказала соответствие **точному head-коммиту успешно проверенного PR**.

В таком случае Pages всё равно:

- заново собирает настоящий production artifact;
- проверяет обязательные статические/Legacy-контракты;
- выполняет короткий production smoke;
- публикует только после успешной проверки.

Если точное подтверждение не найдено — например, direct push, manual dispatch, несовпадение head или изменившийся workflow — автоматически включается полный fallback-набор проверок.

То есть ускорение публикации не является «пропуском CI»: оно исключает повтор уже доказанного тяжёлого набора только там, где доказательство можно проверить машинно.

## Почему CI распараллелен

В октябре 2026 тяжёлые browser-наборы были разделены на shards/matrix jobs. Это сократило wall-clock время, не удаляя общий контракт:

- Chromium regression выполняется несколькими shards;
- catalog audit и versioned catalog contract разделены;
- Chromium/Firefox/WebKit smoke выполняются независимо;
- WebKit использует закреплённое Playwright-окружение;
- Chromium headless-задачи не устанавливают лишний полный браузер там, где достаточно shell.

Если отдельная оптимизация начинает снижать надёжность или создаёт нестабильность, приоритет остаётся за воспроизводимостью и корректностью, а не за ещё несколькими секундами.

## Что особенно защищается

Проверки проекта намеренно следят за следующими границами:

- маршрут /legacy/ не должен незаметно получать Modern-поведение;
- Modern не должен заменять исходные формулы собственной неподтверждённой математикой;
- старый сохранённый билд не должен сам перейти на новый каталог;
- PWA-обновление не должно терять локальные билды или ломать offline boot;
- локализация не должна менять технические ID или игровые числа;
- изменение пользовательского интерфейса не должно случайно экипировать предмет только из-за hover/preview;
- новый release не должен показывать версию, которая расходится с публичным changelog.

## Release metadata

Начиная с Modern 3.11 верхний датированный release-блок в CHANGELOG.md является единым источником публичной версии.

Из него при сборке формируются:

- номер Remaked UI;
- RU/EN пункты окна **Что нового / What’s new**;
- версия PWA-кэша.

Это тоже проверяется автоматическими тестами, чтобы версия сайта и описание обновления снова не разъехались вручную.
